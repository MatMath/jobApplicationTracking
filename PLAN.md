# Job Application Tracker — Build Plan (v2)

> Supersedes `initialPlan.md`. v2 folds in the data model recovered from
> `jobApplicationTracking_old` (Node/Express/Mongo, ~2019-2021) and resolves the
> open either/or choices left in v1.

## Overview
A web app for tracking job applications through a pipeline, with a stats dashboard
as a core feature. Single-user-per-account (auth required), no team/multi-tenant
features.

---

## What changed from v1, and why

The old system tracked real data that v1 dropped. Recovered from
`src/data/types.ts`, `src/data/joiStructure.ts`, and the three CRUD handlers:

| Recovered | v1 status | Decision in v2 |
|---|---|---|
| `meeting[]` — date, participants, purpose, **challenge**, notes | absent | **MVP.** New `meetings` table + UI. Multi-round interviews are not a single "Interview" status. |
| `applicationType`: Recruiters \| Direct | absent | **MVP.** Column on `applications`. Orthogonal to platform. |
| Recruiters entity (full CRUD) | Phase 2 | **MVP.** Merged with v1's planned `contacts` into one `contacts` table with a `kind` discriminator. |
| Company entity (name, location, gps, contact, link) | free text | **MVP.** Normalized `companies` table. Free text fragments per-company stats on typos. |
| `description` (job description body) | absent | **MVP.** Column. Postings get deleted; the URL alone rots. |
| `acceptedOffer` | absent | **MVP.** Folded into an `outcome` column. |
| `answer_receive` | inferred from history | **MVP.** Explicit `first_response_at` timestamp. A rejection *is* a response; inferring it from status transitions misses that. |
| `gps` on company | absent | Phase 2 (map view). Stored as `lat`/`lng` now so the data is there. |
| `/json/param` distinct-value lists | absent | **MVP.** Cheap autocomplete off your own history. |
| `cover_letter` as inline text | file upload only | **Both.** Text column *and* `documents` for file versions. |

Both old analytics endpoints (`/analytic/website`, `/analytic/title`) are already
covered by v1's dashboard spec — no gap there.

### Three fixes to v1 unrelated to the old repo

1. **Row Level Security was never mentioned.** The old app filtered `userId` on
   every query by hand. The Postgres equivalent is RLS, and its absence in a
   Supabase app is a live data-leak risk. Specified below, and non-optional.
2. **Auth: Supabase Auth, Google SSO only.** v1 planned email/password
   alongside Google; v2 drops passwords entirely. Nothing to phish, leak, hash,
   reset, or store, and account recovery becomes Google's problem. RLS also
   depends on this: policies compare `user_id` against `auth.uid()`, which only
   resolves for a Supabase-issued JWT.

   New users are provisioned by an `on auth.users` database trigger that writes
   a `profiles` row inside the same transaction that creates the auth user, so a
   signed-in user always has one — there is no window where the app holds a
   session without a profile. The old system did this at the application layer
   in passport's `serializeUser`; a trigger is the version a second sign-in path
   cannot bypass.

3. **Unresolved choices, now decided** (a plan that says "A or B" defers work):
   - **Data fetching:** React Server Components for reads, Server Actions for
     writes. TanStack Query *only* on the kanban board, where optimistic drag
     updates need a client cache.
   - **Charts:** Recharts. shadcn/ui's chart primitives wrap it, so it composes
     with the rest of the UI; Tremor would be a second, overlapping design system.

## Tech Stack

| Layer | Choice |
|---|---|
| Framework | Next.js (App Router) + TypeScript |
| Styling/UI | Tailwind CSS + shadcn/ui |
| Database | Supabase Postgres (single hosted project) |
| Auth | Supabase Auth — Google SSO only, no passwords |
| ORM | Drizzle |
| File storage | Supabase Storage |
| Hosting | Google Cloud Run (container from `Dockerfile`, deployed by Cloud Build) |
| Data fetching | RSC + Server Actions; dashboard via one `security invoker` SQL function over RPC |
| Charts | Recharts |
| Tests | Vitest (unit + aggregation queries against a throwaway DB) |

### Why Drizzle
- Schema defined once in TypeScript; queries type-checked at compile time.
- Migrations generated by diffing schema against the live DB.
- Queries stay close to real SQL — matters here, since the dashboard is mostly
  custom `GROUP BY` aggregation.

---

### Dashboard aggregation: SQL function over RPC, not Drizzle

v2 planned Drizzle over `DATABASE_URL` for the dashboard. It ships instead as
`public.dashboard_stats()` (`supabase/003_dashboard.sql`), called through the
Supabase client. The GROUP BY work is still SQL; what changes is the security
model. The function is `security invoker`, so RLS scopes every table it reads to
the caller - no hand-written user predicate, and nothing to forget. A Drizzle
connection authenticates as table owner and bypasses RLS, and would have put a
database password into the production runtime for the sake of one page. It also
connects to `db.<ref>.supabase.co`, which Supabase serves over IPv6 only.
Production now needs no credential that can read another user's rows.

Drizzle stays as the schema source of truth and for types.

## Core Features (MVP)

- **Application entries**: company (FK), role, description, job URL, salary range
  + currency, location, remote type, date applied
- **Application type**: recruiter-sourced vs direct
- **Source/platform tracking**: `platform_found` (where discovered) and
  `platform_applied` (where submitted) — these differ often enough to matter
- **Companies**: normalized, reusable, with location/link/notes
- **Contacts**: recruiters, referrals, hiring managers — reusable across applications
- **Meetings**: per interview round — date, purpose, participants, technical
  challenge, notes, outcome
- **Status pipeline** (kanban): Wishlist → Applied → Phone Screen → Interview →
  Offer → Rejected → Withdrawn, with `outcome` capturing accepted/declined
- **Notes** per application (free text, timestamped)
- **Documents**: resume/cover-letter versions per application
- **Search, filter, sort**: status, company, platform, type, date
- **Dashboard** (see below)

## Explicitly Out of Scope
- Reminders / follow-up notifications
- Browser extension / bookmarklet capture
- Email parsing / inbox integration
- Any AI/LLM features (auto-extraction, resume matching, drafted emails)

## Phase 2
- Company map view (the `lat`/`lng` columns exist from day one)
- Calendar view for interviews
- Timeline view per application
- Tags (remote, dream job, referral)
- CSV / JSON import + export

## Dashboard Requirements

Computed via SQL aggregation (`GROUP BY`), not client-side reduction.

**Funnel & conversion**
- Overall response rate, and response rate by platform
- Conversion at each stage (Applied → Screen → Interview → Offer)
- Which platform produces the most *offers*, not just the most applications
- **Recruiter vs direct**: response rate and offer rate *(new — from `applicationType`)*

**Time-based**
- Applications per week/month
- Average time-to-first-response, overall and by platform
- Average time in each pipeline stage
- Oldest application still awaiting a response

**Interview process** *(new — powered by `meetings`)*
- Average number of rounds to reach an offer
- Most common challenge types, and which correlate with advancing
- Which interview purposes you most often stall at

**Motivational / fun**
- Ghosting rate: % with no response after 30 days, by platform
- Busiest application day of the week
- Streak: consecutive days/weeks with at least one application
- Salary applied-to vs. salary that converted to interviews
- Top 3 companies/platforms by response rate

**Patterns**
- Most-applied-to role titles (the old `/analytic/title` query)
- Remote vs hybrid vs onsite split, and which converts better

## Database Schema

Every table carries `user_id` directly — including child tables. Denormalizing it
onto `meetings`/`notes`/`documents`/`status_history` keeps RLS policies to a
single indexed predicate instead of a join back through `applications`.

```ts
// companies
export const companies = pgTable('companies', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  name: text('name').notNull(),
  location: text('location'),
  lat: doublePrecision('lat'),          // Phase 2 map; old system stored GeoJSON
  lng: doublePrecision('lng'),
  website: text('website'),
  notes: text('notes'),
  createdAt: timestamp('created_at').defaultNow(),
}, (t) => ({
  uniqPerUser: unique().on(t.userId, t.name),   // stops typo-fragmented stats
}));

// contacts — old `recruiters` collection merged with v1's planned `contacts`
export const contacts = pgTable('contacts', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  name: text('name').notNull(),
  kind: text('kind'),                   // recruiter | referral | hiring_manager | other
  agency: text('agency'),               // old `cie`: firm the recruiter works for
  companyId: uuid('company_id').references(() => companies.id),
  email: text('email'),
  phone: text('phone'),
  notes: text('notes'),
  createdAt: timestamp('created_at').defaultNow(),
});

// applications
export const applications = pgTable('applications', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  companyId: uuid('company_id').notNull().references(() => companies.id),
  role: text('role').notNull(),
  description: text('description'),     // restored: postings get deleted
  jobUrl: text('job_url'),
  applicationType: text('application_type'),  // recruiter | direct
  recruiterId: uuid('recruiter_id').references(() => contacts.id),
  platformFound: text('platform_found'),
  platformApplied: text('platform_applied'),
  location: text('location'),
  remoteType: text('remote_type'),      // remote | hybrid | onsite
  salaryMin: integer('salary_min'),
  salaryMax: integer('salary_max'),
  salaryCurrency: text('salary_currency').default('CAD'),
  coverLetter: text('cover_letter'),    // restored: old stored it inline as text
  status: text('status').notNull().default('wishlist'),
  outcome: text('outcome'),             // accepted | declined | rejected | withdrawn | ghosted
  rejectionReason: text('rejection_reason'),
  appliedAt: timestamp('applied_at'),
  firstResponseAt: timestamp('first_response_at'),  // explicit; a rejection counts
  closedAt: timestamp('closed_at'),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow(),
});

// meetings — restored from old `MeetingInfo[]`, the richest data v1 dropped
export const meetings = pgTable('meetings', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  applicationId: uuid('application_id').notNull()
    .references(() => applications.id, { onDelete: 'cascade' }),
  scheduledAt: timestamp('scheduled_at'),
  purpose: text('purpose'),             // phone_screen | technical | behavioral | onsite | final | other
  participants: text('participants').array(),  // free text, matching old string[]
  challenge: text('challenge'),         // the technical challenge given
  outcome: text('outcome'),             // pending | passed | failed
  notes: text('notes'),
  createdAt: timestamp('created_at').defaultNow(),
});

// status_history — powers timeline + time-in-stage
export const statusHistory = pgTable('status_history', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  applicationId: uuid('application_id').notNull()
    .references(() => applications.id, { onDelete: 'cascade' }),
  status: text('status').notNull(),
  changedAt: timestamp('changed_at').defaultNow(),
});

// notes
export const notes = pgTable('notes', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  applicationId: uuid('application_id').notNull()
    .references(() => applications.id, { onDelete: 'cascade' }),
  content: text('content').notNull(),
  createdAt: timestamp('created_at').defaultNow(),
});

// documents
export const documents = pgTable('documents', {
  id: uuid('id').defaultRandom().primaryKey(),
  userId: uuid('user_id').notNull(),
  applicationId: uuid('application_id').notNull()
    .references(() => applications.id, { onDelete: 'cascade' }),
  fileName: text('file_name').notNull(),
  fileUrl: text('file_url').notNull(),
  type: text('type'),                   // resume | cover_letter | other
  uploadedAt: timestamp('uploaded_at').defaultNow(),
});
```

Indexes: `user_id` on every table; `(user_id, status)` and `(user_id, applied_at)`
on `applications`; `application_id` on all children.

### Row Level Security

Not optional, and now the primary enforcement boundary rather than a second layer.
The publishable key ships to the browser, so without RLS any authenticated user
could read every other user's rows. Applied to all seven tables by
`supabase/bootstrap.sql`:

```sql
alter table public.applications enable row level security;
create policy owner_all on public.applications for all to authenticated
  using (user_id = (select auth.uid()))
  with check (user_id = (select auth.uid()));
```

`(select auth.uid())` rather than a bare `auth.uid()` is deliberate: the wrapped
form is evaluated once per query instead of once per row, which matters on the
dashboard's aggregate scans.

Queries that go through `DATABASE_URL` (Drizzle, for dashboard aggregation)
connect as the table owner and **bypass RLS**. Those paths must scope by user in
the query itself, which is what `src/db/scope.ts` enforces — the old system
hand-wrote `{ userId: req.user.userId }` on every query, and a single omission
there would have leaked another user's rows.

Tests assert that a second user's rows are invisible through both paths.

## Development Setup

One Supabase project serves both development and production. There is no local
database and no Docker.

1. Create the project at <https://supabase.com/dashboard>.
2. Run `supabase/bootstrap.sql` in the SQL editor — creates every table, index,
   the `updated_at` trigger, and the RLS policies.
3. Fill `.env` (see `.env.example`): project URL, publishable key, secret key,
   and `DATABASE_URL` from Settings → Database → Connection string.
4. `npm install && npm run dev`.

`supabase/bootstrap.sql` is hand-written to mirror `src/db/schema.ts` because
`drizzle-kit` needs Node. Once Node is installed, `npm run db:push` diffs the two;
a no-op result confirms they agree, and from then on Drizzle owns migrations.

**Two keys, two jobs.** The publishable key is browser-safe and fully subject to
RLS. The secret key bypasses RLS entirely — it stays server-side, is never
imported into a client component, and is not prefixed `NEXT_PUBLIC_`.

**A caveat worth stating plainly:** with a single shared project, development
writes land in the same database as real data. Before this holds anything you
care about, add a second Supabase project for production and point `.env` at the
dev one. Cheap now, painful later.

### Prerequisites
- **Node.js 20+** — not currently installed; nothing can be installed or run
  without it. The bootstrap SQL is the one step that works without it.

## Build Order

Each step ends in a commit.

1. **Scaffold** — Next.js + TS + Tailwind + shadcn/ui, `.env.example`,
   Drizzle config, `supabase/bootstrap.sql`
2. **Schema + migrations** — all tables above, indexes, seed script with
   realistic fake data (so the dashboard has something to show from day one)
3. **Auth** — Supabase Auth via `@supabase/ssr`, middleware session refresh,
   protected route group
4. **Companies + contacts CRUD** — needed before applications can reference them
5. **Application CRUD** — full form, autocomplete off distinct existing values
6. **Kanban board** — drag-to-update-status, writing `status_history` and
   stamping `first_response_at` on the first non-wishlist/applied transition
7. **Meetings UI** — add/edit rounds on the application detail page
8. **Notes + document upload**
9. **Search / filter / sort** on the list view
10. **Dashboard** — response rate by platform and apps-per-week first, then
    recruiter-vs-direct and the interview-process stats, then the rest
11. **Polish** — empty states, loading states, mobile
